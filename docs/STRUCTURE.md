## 왜 이렇게 나눴나 (실행 순서 보존)

원본은 script **한 개**라서 함수 선언이 맨 앞으로 끌어올려졌습니다(hoisting). 파일을 나누면 각 파일은 자기 차례에만 함수를 만들기 때문에, 앞 파일이 뒤 파일의 함수를 **바로 실행하거나 감싸면** 결과가 달라집니다.
그래서 최상위 문장마다 "읽히는 순간 실행되는 코드"가 어떤 이름을 쓰는지(호출되는 함수의 몸통까지 따라가며) 계산했고, 그 결과는 다음과 같습니다.

- 실행되는 문장(함수 선언이 아닌 것)은 **원본 순서 그대로** 파일 경계만 넣었다 — 2,618개 문장 중 지운 2개를 뺀 나머지의 순서·내용이 원본과 같다(덮어써져 실행되지 않던 옛 선언 2개는 지움, 아래) (`docs/VERIFICATION.md`)
- 순서 제약을 만드는 이름은 5개뿐이었다. 함수 선언은 원래 끌어올려지므로 **선언 위치만 앞 파일로 옮기면** 원본과 같다

| 함수 | 원본 위치 | 먼저 쓰는 곳 | 옮긴 곳 |
|---|---|---|---|
| `jo2` (조사 처리) | 바탕 `desking.js` 구획 | `articles.js`의 데이터 준비가 바로 호출 | `src/core/utils.js` |
| `eraGen` | 꼬리 `era-front.js` | 모듈 `v15.js`가 감쌈 | `src/compat/_hoisted.js` |
| `eraBox` | 꼬리 `era-front.js` | 모듈 `v18.js`가 감쌈 | `src/compat/_hoisted.js` |
| `migrate` | 꼬리 `main.js` | 1.6 모듈(`r16-fixes.js` 등)이 감쌈 | `src/compat/_hoisted.js` |
| `deptsFor` | `base-data.js` 안 | 같은 파일 안 | (안 옮김) |

원래 자리에는 `/* [옮김] … */` 주석을 남겼습니다.

- **덮어써진 옛 선언 정리** `bribeEvent`·`bribeOut`: 바탕(`actions.js`·`npc.js`)에 옛 봉투 이벤트가, 1.5 개편(`r15-goals-favor.js`)에 새 판이 같은 이름으로 있었습니다. 원본에선 끌어올림 때문에 처음부터 새 판만 쓰였으므로 옛 판은 실행되지 않는 코드였습니다. 지우고 그 자리에 한 줄 주석을 남겼습니다(읽히는 시점에 이 이름을 쓰는 코드가 없음을 계산으로 확인, `vstatic.mjs`가 이 두 선언만 빼고 원본과 같은지 비교).

### 바탕 게임은 왜 기능별, 모듈은 왜 버전별인가

바탕 게임은 원본의 구획 주석을 경계로 큰 기능 단위 파일(core·data·systems·ui)로 나눴습니다. 경계는 순서 제약 계산에서 안전한 곳만 골랐습니다.
1.x 모듈은 앞 코드를 감싸고 덮어쓰는 **순서 자체가 의미**라서 기능별로 다시 묶지 않고 원본 순서대로 `src/compat/`에 두었습니다.
- 1.42까지는 원본 소스의 모듈과 1:1(`v13a.js`~`v42.js`)
- 1.5~1.6은 이웃한 모듈을 릴리스·주제별로 **순서 그대로 이어 붙였습니다** — `r15-goals-favor.js`(예전 v43·v44), `r16-org.js`(v45~v48), `r16-fixes.js`(v49·v50), `r16-ai-ui.js`(v51~v60). 파일 안에 `// ───── (예전 v45.js) ─────` 표시가 남아 있습니다. 합친 뒤에도 끌어올림 위반 0, 원본과 문장 순서·내용 같음(아래 검증)
- 나중에 더 합치거나 기능별로 옮기고 싶다면 한 모듈씩, 래퍼 순서를 지키면서 옮겨야 합니다

## 테스트

`npm test` — 정적 검사 → 빌드 → 브라우저(Playwright)로 시나리오 8개를 같은 난수로 돌립니다.
- `dist/`와 `dist-single/`의 결과 상태가 같은지
- 저장해 둔 기준값(`tests/golden.json`)과 같은지 — 게임을 일부러 바꿨다면 `npm run test:update`로 기준값을 새로 씁니다
- 매달 점검: 숫자 NaN · 한 사람이 두 부서에 · 명부에서 사라진 팀원 · 재무 합계 불일치
- 저장 → 새 창에서 불러오기: 불러온 직후 상태가 저장 전과 같고, 이어서 3개월을 해도 오류가 없는지

`npm run test:quick`은 저장 시나리오 2개만 돌립니다. 처음 한 번 `npm i -D playwright && npx playwright install chromium`이 필요합니다.

## 빌드 도구

`scripts/` (Node 기본 모듈만 사용)
- `serve.mjs` 정적 서버 (mp3 Range 요청 지원)
- `build.mjs` `dist/` 복사 + `dist-single/` 합치기 (그림·글꼴을 다시 data URI로, CSS·JS를 원래 자리에)
- `check.mjs` 문법(`node --check`)·참조·해시 검사
- `tests/run.mjs` 자동 회귀 테스트(`npm test`) — 아래 「테스트」

Vite 같은 번들러는 쓰지 않았습니다. 게임 코드가 전역 이름을 공유하는 일반 script라서 묶을 필요가 없고, 이 작업 환경에선 npm 패키지를 받을 수 없어 Vite 명령을 실제로 검증할 수 없었기 때문입니다. 위 명령들은 모두 실제로 실행해 확인했습니다.

`tools/refactor/`에는 이번 분리에 쓴 스크립트(`split.mjs`, 옛 선언 정리 `dead.mjs`, 1.5~1.6 모듈 합치기 `merge.mjs`, 끌어올림 분석 `vhoist.mjs`, 원본 대비 비교 `vstatic.mjs`, 브라우저 비교 `*.py`)를 참고용으로 넣었습니다. 경로가 작업 환경에 맞춰져 있어 그대로 돌리려면 경로를 고쳐야 합니다.
